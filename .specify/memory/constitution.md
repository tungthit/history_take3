# Chill Geo-Flight Constitution

This document records how the repository works and where the owner wants the project to go. The
vision principles (I-III) state the owner's direction. The rest record current practice.

## Core Principles

### I. History Browsing Is the Product
The purpose of the project is to let a person browse history through many aspects, easily. Each
aspect is its own thread, such as the history of computing or the history of pathology and
medicine. The 3D globe and every other graphic are the presentation layer for this knowledge.
They are not the goal. A feature MUST be judged by whether it helps people explore history, not by
how impressive it looks.

### II. Knowledge Before Visuals
Good knowledge comes first. Visual work on an aspect starts only after its data is good.
- For now the knowledge comes from Wikipedia and other reputable sources. Official data MUST be
  chosen where it exists.
- Each aspect needs a rich timeline: many dated milestones, not a handful.
- Data modules (`scistory.js`, `history.js` and the others) hold the knowledge. The visual code
  reads them and does not invent facts.

Rationale: a polished visual on weak data spreads weak history.

### III. Accurate Visuals, No Untrue Content
Any 2D image, 3D model or animation MUST show the subject accurately. Content MUST NOT be made "just
to have something". If a subject cannot be shown accurately with the data and skill available, it
MUST be left out or shown in a clearly simpler and honest way (for example a plain label), not drawn
approximately. Untrue content is never acceptable. When in doubt about a fact, check the source
before drawing it.

### IV. Static Site on GitHub Pages, Committed Build Output
The game is a static site with no backend. Production is served directly from GitHub Pages at
https://tungthit.github.io/history_take3/ from the `docs/` folder of `main`. `docs/` (plain HTML
plus prebuilt JS, CSS and images) is generated by Vite and committed to git. Every URL is
relative (`base: './'`), so the site works from the Pages sub-path `/history_take3/` and from any
other folder. Changes to `source/` are only considered done once `docs/` has been rebuilt.

### V. three.js Is the 3D Engine
All 3D rendering of the globe and the flight uses three.js (pinned at 0.169.0) in WebGL. It is the
presentation layer described in Principle I. The scene, renderer and camera are owned by
`engine.js`. Modules that touch the scene import it as `import * as THREE from 'three'`
(`engine.js`, `globe.js`, `detail.js`, `layers.js`, `landmarks.js`, `models.js`).
- The globe, trails, nav lights and city glow are drawn with `THREE.ShaderMaterial` and custom
  GLSL, with data textures such as the day, night, country-id and relief maps passed as uniforms.
- Full-resolution imagery is streamed through the render-target atlas in `detail.js`, so only
  a window of tiles is held on the GPU.
- React renders the UI around the canvas. It does not replace three.js for 3D drawing.

### VI. Source Lives in `source/`, Game Code in `source/src/geoflight/`
Game code is organized by feature inside `source/src/geoflight/`, in flat modules:
- Engine and rendering: `engine.js`, `globe.js`, `models.js`, `detail.js`, `layers.js`.
- Data modules (the knowledge): `landmarks.js`, `places.js`, `history.js` and `history/`,
  `scistory.js`, `branches.js`.
- React UI: `GeoFlight.jsx`, `SciStory.jsx`.
- Science illustrations: `art*.jsx`, aggregated in `artall.js`.
- Audio and speech: `audio.js`, `speech.js`.
- Styles and bundled assets: `geoflight.css`, `assets/`.

Large static map data (terrain tiles, road/rail/water layers) lives in `source/public/geoflight/`
and is served as-is.

### VII. Naming Conventions
- React component files use PascalCase with the `.jsx` extension (`GeoFlight.jsx`, `SciStory.jsx`).
- Non-component modules use lowercase names with the `.js` extension (`engine.js`, `globe.js`).
- Illustration modules are prefixed `art` plus a subject (`artmath`, `artphys`, `artbio`,
  `artmed`) and are merged by id into one `ART` map in `artall.js`.

### VIII. Reproducible Builds with Pinned Dependencies
The app is built with Vite from `source/` (`npm install`, then `npm run build`), which rewrites
`docs/`. Dependencies are pinned to exact versions in `source/package.json` (React 18.3.1,
three 0.169.0, Vite 6.4.1, `@vitejs/plugin-react` 4.7.0), with `package-lock.json` committed.
The README documents how to serve `docs/` locally with any static server. `file://` is not
supported because browsers block loading textures and data from disk.

### IX. Heavy Data Is Baked Offline, Not Computed at Run Time
Static assets (country and place data, terrain tiles, layers, flags, textures) are produced by
the scripts in `tools/geoflight-bake/` (`bake.mjs`, `bake-layers.mjs`, ES modules on Node).
The baked output is committed, and the baker is run only when the data changes. Each external
data source and its licence is listed in `tools/geoflight-bake/README.md`. Third-party assets
keep their own licence files (e.g. `assets/flags/LICENSE.txt`).

### X. English Is the Primary Language
The shipped product uses English as its main language. All user-facing UI text, labels, stories
and narration are in English. Other languages are for reference only. When another language is
needed to explain a term or a source, it is quoted alongside the English text and is not the
primary content.

## Stack & Constraints

- **Language and runtime**: JavaScript (ESM) with JSX. There is no TypeScript.
- **Libraries**: React 18 for the UI, three.js for 3D (see Principle V), Vite for bundling.
- **Hosting**: GitHub Pages, static files only (see Principle IV).
- **Knowledge sources**: Wikipedia and other reputable sources, with official data preferred
  (see Principle II).
- **Attribution**: the project is a web migration based on *Geographical Adventures* by
  Sebastian Lague (MIT). The README credits him and the original sources.
- **Third-party data**: only public-domain or openly licensed sources (Natural Earth, NASA,
  Mapzen/AWS terrain tiles, `flag-icons`), with credits kept in the README or the baker README.

## Development Workflow

- Work happens on feature or chore branches that are merged into `main`. Production is what
  `main` holds in `docs/`.
- Commit messages are short and imperative, optionally with a `chore:` prefix.
- For a new history aspect, the knowledge and timeline are reviewed before any visual work
  starts (Principle II).
- The repo currently has no CI, linter, formatter or automated test suite. Changes are checked
  by building and running the result from a static server. This constitution does not introduce
  those tools.
- The repo uses Spec Kit (`.specify/`, `.claude/skills/speckit-*`) for specs and plans.

## Governance

This constitution ranks above ad-hoc preferences. To amend it, update
`.specify/memory/constitution.md` in a pull request that states why the change is needed, and bump
the version:
- MAJOR: a principle is removed or redefined incompatibly.
- MINOR: a principle or section is added or materially expanded.
- PATCH: wording or clarification only.

Reviewers MUST check that changes follow these principles. In particular they MUST check that
new knowledge comes from an acceptable source (Principle II) and that new visuals are accurate
(Principle III). If the repo adopts CI, lint or tests later, this document MUST be amended to
record them.
